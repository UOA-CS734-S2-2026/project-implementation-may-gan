## Outcome

### Problem and context

Recipients and operators have no actor-wide new-message protection across the two creation paths. Current request-state, auth and socket limits do not satisfy this rule. Evidence: current action transaction/service paths and closed #127's historical audit.

### This ticket aims to

Enforce the exact sender-wide sliding-window rule in [the quota specification](../spec.md) without charging exact retries or changing other actions.

## Scope

Both message-creation endpoints; shared persistent count-and-insert enforcement; sender advisory lock after existing pair/conversation locks; current PostgreSQL time; additive sender/time index; server-only configuration; documented 429/retry guidance and generated clients.

## Exclusions

General anti-abuse redesign, edits, reactions, reads, request resolution, sockets, friend requests and notification implementation.

## Acceptance criteria

- [ ] Default is 30 new messages per sender in a rolling 60 seconds across both endpoints and conversations. All accepted rows count, including unsent tombstones.
- [ ] Hold a namespaced sender advisory transaction lock after existing pair/conversation locks; sample fresh PostgreSQL time after lock acquisition for the count and accepted timestamp. Do not use transaction-start `now()` or a pre-lock Worker clock for the rolling decision.
- [ ] Count rows at or after the lower boundary, as the approved plan specifies. Test the exact boundary and first eligible instant after it.
- [ ] More than 30 concurrent authorized first/existing-thread sends across independent connections persist at most 30 messages. Other senders remain independently eligible.
- [ ] Exact idempotent replay returns the current canonical result before quota checks. Conflicting ID reuse remains 409. Rejected authorization/state/text/reply requests create no quota-consuming row.
- [ ] 429 includes positive retry guidance in the documented error contract and `Retry-After`; both endpoints and regenerated TS/Dart contracts agree.
- [ ] Server-only `DIRECT_MESSAGE_SEND_LIMIT` defaults to 30 for missing/malformed/negative/non-integer/unsafe values, accepts positive safe integers, and uses `0` to disable. Update config generators/examples and runbook.
- [ ] Additive sender/time index, migration reviews and restricted-role tests pass. Assign migration number only after integrating current main, without altering deployed history.

## Edge case

The sender reaches quota, retries a saved accepted request successfully, then sends a fresh request just after the oldest counted row leaves the inclusive 60-second window. Only the new request consumes a slot.
