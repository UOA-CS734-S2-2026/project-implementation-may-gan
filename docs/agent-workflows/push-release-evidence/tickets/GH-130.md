## Outcome

### Problem and context

Local Flutter tests do not prove Android/iOS banners, APNs delivery, cold-start routing or old-account isolation. Users could miss notifications or encounter an unsafe tap. Current #130 still requires foreground suppression and generic previews, contrary to the approved platform behavior.

### This ticket aims to

Collect sanitized physical Android/iOS evidence for [the release spec](../spec.md) using the implemented generic notification platform, not duplicate its implementation.

## Dependency

GH-141, MN-003, MN-004, MN-005. MN-001/MN-002/GH-034 are transitive prerequisites. Approved physical devices, staging accounts, compatible builds and owner-authorized test sends are external gates.

## Scope

Permission/consent, registration and token rotation, logout/account replacement, foreground OS banners, background/terminated OS presentation, and cold/warm authorized taps for all four event categories.

## Exclusions

No provisioning, secret writes, production tests, new client/server implementation, browser push, offline sends or background sockets. Failures return to the owning ticket or an approved follow-up.

## Acceptance criteria

- [ ] On both platforms, default-off account preference and denied OS permission prevent delivery/registration as appropriate; neither repeatedly prompts nor breaks foreground messaging.
- [ ] On both platforms, opt-in and valid registration prove direct messages, friend requests, final-hour reminders and midnight release notices in foreground/background/terminated states.
- [ ] Foreground displays an OS banner, not silent refresh only. Verify no duplicate local/provider presentation for the same received event; do not claim exactly-once provider delivery.
- [ ] Message previews contain current sender name/text; friend requests contain sender name/fixed request wording; daily notices expose no private content. Edited/unsent queued-message cases match policy.
- [ ] Taps wait for session resolution and an authorized REST preflight before navigating to conversation, incoming requests, composer or friends feed. Unauthorized/stale and malformed payloads fail safely.
- [ ] Token refresh, opt-out, logout, expired/replaced sessions and account switch cannot revive old subscriptions, pending callbacks or private caches.
- [ ] Record platform/build/deployed commit, timestamp, scenario pass/fail and sanitized observations. No credentials, tokens, account/resource IDs, private messages or revealing screenshots enter evidence.

## Edge case

A stale old-account notification is tapped after account replacement. No old-account state is recovered; authorized preflight under the current epoch either succeeds legitimately or falls back safely.

## Entry points

`apps/mobile/lib/notifications/`, session controller/composition, generic platform publishers, owner-managed native staging configuration, evidence runbook.

## Validation

Flutter analysis/unit/widget suites plus approved physical Android/iOS matrix. Scheduled cases must exercise actual staging scheduler/provider behavior, not merely alter a device clock or fabricate a push. Local mocks cannot satisfy device acceptance.

## Risk and rollback

Disable notification feature flag and retain foreground messaging. Clear local presentation state where platform APIs allow; already delivered previews cannot be recalled universally.
