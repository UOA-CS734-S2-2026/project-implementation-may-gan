# MN-002: Deliver direct-message previews through the shared notification service

## Description

### Problem and context

The message publisher and FCM adapter currently assume generic conversation-only push. They cannot deliver the approved sender/text preview or support other publishers. Users also risk duplicate banners during a server cutover. Evidence: `append-conversation-change.ts`, `messaging-delivery-runtime.ts`, and `fcm.ts`.

### This ticket aims to

Prove the generic server notification path with a new-message slice, preserving legacy delivery without duplicate jobs, as required by [the specification](../spec.md).

## Scope and exclusions

Internal typed publishers, leased notification dispatcher, message event publication, current-preview resolution, capability routing, safe FCM normalization, disabled flag, and repair/immediate dispatch. Keep `messaging_outbox` schema and realtime semantics intact. Exclude other publishers, Flutter implementation, real provider tests, and public arbitrary-send APIs.

## Acceptance Criteria

- [ ] New messages on both creation endpoints atomically publish one logical notification intent with the source transaction. Replays, edits, reactions, reads, and sockets do not publish new notifications. Rollback removes both source and intent.
- [ ] Before dispatch, recheck recipient account, session, registration, account preference, device eligibility, membership, block state, message existence and unsent state. The account preference gates legacy and new delivery alike.
- [ ] Capable devices use only new-format delivery; legacy devices use only legacy message delivery after account opt-in. No device gets both for the same source event, including queued legacy jobs during cutover.
- [ ] Fetch sender display name and current message text at dispatch, not from copied outbox text. An edit changes the queued preview; unsend suppresses it. Already delivered banners cannot be recalled.
- [ ] FCM receives the approved versioned type/target envelope and preview. Tokens, sender names, message text, and provider response bodies never enter logs/errors/evidence.
- [ ] Current standard Firebase service-account credentials are safely normalized for the sender. Missing/malformed configuration or feature disable prevents sends and does not block realtime delivery.
- [ ] Fenced leases, bounded retries, permanent token rejection, suppression, and provider failure are covered by tests. Network calls occur only after commit using fresh invocation-owned clients.

## High Risk?

Message preview disclosure, session isolation, migration cutover, and persistent fan-out. No E2EE, Firebase Auth, GraphQL, or FCM topics are asserted.
