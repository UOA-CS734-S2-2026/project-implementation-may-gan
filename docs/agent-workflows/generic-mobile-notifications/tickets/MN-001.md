# MN-001: Add owner consent and notification capability registration

## Description

### Problem and context

Mobile users have only per-device push opt-in today. There is no account-wide preference or payload capability, so an updated server cannot safely distinguish legacy devices or apply the approved default-off consent rule. Evidence: `push_devices` schema and the existing registration API. Notification persistence also assumes a conversation, preventing unrelated publishers from using it.

### This ticket aims to

Provide owner-only consent APIs and backward-compatible capability registration, backed by additive notification storage, as the disabled expand step of [the specification](../spec.md).

## Scope and exclusions

Add account preferences, event/delivery tables, restricted-role access, unique event/destination identity, schema capability on device registration, and a default-disabled server notification flag. Return preference false for accounts without a preference row. Exclude publishers, FCM sends, Flutter settings, and production activation.

## Acceptance Criteria

- [ ] Authenticated owners can read/change only their own global preference. New and existing accounts default off.
- [ ] Registration accepts the supported payload schema version; old requests remain valid legacy registrations. Unsupported/malformed versions are rejected safely.
- [ ] Logical events and per-device deliveries support the four approved types, opaque source/target references, unique deduplication keys, expiry, and fenced retry state without copied message text.
- [ ] Additive migrations, indexes, grants, schema exports, and generated clients pass isolated PostgreSQL and contract checks. Allocate migration numbers after integration, not from this dirty checkout.
- [ ] Missing or malformed notification feature configuration leaves publishers disabled. The DB-free contract app remains DB-free.
- [ ] A foreign user's attempt cannot read or change another account's consent. Tests cover missing rows and old registration bodies.

## High Risk?

Account/session authorization, preview privacy, and persistent fan-out. The template's Firebase Auth, GraphQL, E2EE, and topic-subscription examples do not describe this stack. Use Better Auth, Hono, PostgreSQL, and per-device FCM.
