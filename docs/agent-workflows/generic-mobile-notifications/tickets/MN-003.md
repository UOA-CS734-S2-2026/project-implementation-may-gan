# MN-003: Add Flutter notification consent, foreground banners, and safe taps

## Description

### Problem and context

Flutter refreshes the inbox silently for foreground FCM and routes taps using only a conversation ID. Users cannot enable the new account preference or safely navigate other notification categories. Evidence: `FirebasePushLifecycle`, `NotificationRouter`, and the current composition root.

### This ticket aims to

Give users one account-level setting and a reusable foreground OS-banner/tap interface for all four approved event categories in [the specification](../spec.md).

## Scope and exclusions

A small platform compatibility spike, notification presenter, schema decoder, consent setting, capability registration, session-fenced preflight routing, and relevant feature refresh. Exclude server publishers, credential provisioning, physical-device release claims, and per-category preferences.

## Acceptance Criteria

- [ ] A minimal Android/iOS plugin spike verifies compatibility with pinned Flutter/Firebase versions and documents one foreground presentation mechanism per platform. Missing native build tooling is a blocker, not a claimed pass.
- [ ] Account consent defaults off and is read from the server. Explicit enablement requests permission and registers capability/token only when granted. Denial does not repeatedly prompt or break messaging.
- [ ] Foreground events show an OS banner through a feature-neutral presenter. Background/terminated events use provider OS presentation. Local and remote tap callbacks share one router; no double presentation is introduced.
- [ ] Typed events route messages to `/messages/:id`, friend requests to `/friends` incoming requests, reminders to `/post`, and releases to `/`. Fetch authorized current destination state before navigation.
- [ ] Unknown versions, malformed targets, network failure, stale/unauthorized targets, expired sessions, and account replacement disclose no cached private content. Pending callbacks are fenced to the current account/session epoch; safe fallback never grants access.
- [ ] Logout/account replacement clear pending tap state, local notifications and in-memory previews as far as platform APIs allow, stop old work, and preserve the existing server-session revocation safeguards.
- [ ] Tests prove all four routes using fakes even before every server publisher exists. Device delivery proof remains #130.

## High Risk?

Authentication, lock-screen preview exposure, notification lifecycle, and account-switch privacy. This feature is not E2EE and does not use Firebase Auth.
