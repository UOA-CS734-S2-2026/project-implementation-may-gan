# MN-004: Notify recipients of pending friend requests

Status: approved ticket scope. Execution is governed by `../run-approval.md`.

Merge mode: auto-merge, subject to CI, local verification, independent review and repository protection.

## Description

### Problem and context

Friend-request creation stores a pending request but queues no mobile notification. Eligible users must open the requests screen to discover it. Evidence: the send-friend-request action and relationship transaction.

### This ticket aims to

Deliver a sender-name request notification to eligible recipients through the internal shared service in [the specification](../spec.md).

## Scope and exclusions

Transactional friend-request publisher, approved fixed request wording with current sender display name, recipient dispatch policy, and source post-commit dispatch. Exclude acceptance/cancellation notifications, new profile discovery, client screens, and arbitrary send APIs.

## Acceptance Criteria

- [ ] A newly pending request and logical event commit together. Failure rolls both back; existing/duplicate requests produce no second event.
- [ ] Only capable eligible recipient devices receive delivery, subject to account opt-in, current registration/session/account and feature flag.
- [ ] Dispatch rechecks that this request remains pending for this recipient and neither direction is blocked. Cancelled, accepted, declined, deleted, and blocked requests suppress safely.
- [ ] Banner includes sender display name and fixed request wording only. Payload target is the authenticated requests destination, not arbitrary URLs or other profile data.
- [ ] Immediate dispatch starts only after commit. Retries and concurrent claims cannot duplicate durable source/destination work.
- [ ] Tests cover cancellation/block racing with dispatch and no sender-device notification.

## High Risk?

Relationship authorization, name disclosure, and event fan-out. No Firebase Auth, GraphQL, E2EE, or FCM topic assumptions apply.
