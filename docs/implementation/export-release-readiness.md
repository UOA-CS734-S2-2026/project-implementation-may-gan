## Historical synthetic-only staging plan (superseded by all-account staging activation)

The earlier proof plan first deployed the restricted worker Hyperdrive with proof variables unset. At that point production, the normal web entry, and native export entry remained disabled. The plan would have admitted one disposable owner using all four `STAGING_EXPORT_PROOF_*` variables: the exact user ID, the `synthetic-only` acknowledgment, a build cutoff no more than one hour ahead, and a cleanup review checkpoint at least 48 hours after the build cutoff. The checkpoint never stops cleanup. Scoped cleanup continues until its database task is confirmed complete and the operator removes the proof settings. Only the reviewed staging configuration emits these variables. Worker claims and cleanup queries are additionally scoped to that owner in append-only migration `0052_staging_export_proof_scope.sql`. No other owner's request or cleanup task should be claimed by the proof runtime.

Under that superseded plan, the operator would have provisioned a synthetic account, set bounded staging proof variables without publishing credentials, and redeployed through the coordinated staging release. Other signed-in owners would still have received 503 for every export route, before testing request, archive, download, expiry, and two cleanup passes. The second pass is due 24 hours after the first. Do not delete the synthetic account until its durable cleanup task has completed; the scoped cleanup query needs the request row to identify the archive. Stopping build while retaining cleanup requires moving the build cutoff into the past. The review checkpoint does not stop cleanup: an archive published at the end of the build window may need its first cleanup pass 24 hours later and its second pass another 24 hours after that. Cron delay or provider retries can make both later. Check that the synthetic owner's ready requests and durable cleanup tasks are gone before removing the proof settings. Removing the acknowledgment stops both immediately but may strand a task, so use that emergency stop only with an incident and recovery plan. The staging proof skips generic incident pruning to avoid changing another account's evidence. An incident requires a separate, reviewed resolution and retention check.

This single-account proof plan was superseded by the reviewed all-account staging release. After [release 37185148166](https://github.com/UOA-CS734-S2-2026/project-implementation-may-gan/actions/runs/37185148166) deployed API and web, the protected synthetic account completed a live request, build, and authenticated ZIP integrity check. [Run 37185441062](https://github.com/UOA-CS734-S2-2026/project-implementation-may-gan/actions/runs/37185441062) accelerated and checked both cleanup passes for that request. This does not prove a real 24-hour wait, late provider completion, or two-owner isolation. The [Android tester APK](https://github.com/UOA-CS734-S2-2026/project-implementation-may-gan/actions/runs/37185315368) built successfully and passed package and signature checks. None of this authorizes real-user registration or claims worldwide privacy compliance.

## Accelerated synthetic cleanup, not a live 48-hour proof

The manual `Accelerate synthetic staging export cleanup` workflow runs only on `main` with the `staging` environment and a verified direct staging database target. Before dispatch, set `STAGING_EXPORT_TEST_OWNER_ID` and `STAGING_EXPORT_TEST_REQUEST_ID` to the owner and request produced by the existing smoke account. The workflow compares the owner's stored email to the protected `SMOKE_TEST_EMAIL` secret. It refuses other accounts, requests older than three hours, and unexpected cleanup states. It reports only a fixed outcome and phase, never an ID, object key, email, or database error.

After a successful synthetic download, dispatch the workflow once. It changes only this ready request's `ready_at` and `expires_at` together so the existing 24-hour constraint holds. In the same run, it waits for the regular Worker cron to record the first provider cleanup pass, advances only this task's second-pass timestamps, then waits until neither the request nor a task under its private object-key digest remains. Each wait has a nine-minute deadline. A failed or timed-out run is not proof of completion. Do not repeat the workflow against an already expired request. Keep cleanup running and investigate. Advancing database clocks does not reproduce a real delayed R2 completion, a 24-hour wait, or an unrelated owner's export. Those limitations remain release evidence gaps.
