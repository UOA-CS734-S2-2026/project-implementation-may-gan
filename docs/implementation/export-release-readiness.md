## Planned staging-only synthetic proof

The staging rollout must be reviewed before use. The first deployment binds the restricted worker Hyperdrive but leaves the proof variables unset. Production, the normal web export entry, and the native export entry remain disabled. A single disposable staging owner can later be admitted with all four `STAGING_EXPORT_PROOF_*` variables: the exact user ID, the `synthetic-only` acknowledgment, a build cutoff no more than one hour ahead, and a cleanup review checkpoint at least 48 hours after the build cutoff. The checkpoint never stops cleanup. Scoped cleanup continues until its database task is confirmed complete and the operator removes the proof settings. Only the reviewed staging configuration emits these variables. Worker claims and cleanup queries are additionally scoped to that owner in append-only migration `0052_staging_export_proof_scope.sql`. No other owner's request or cleanup task should be claimed by the proof runtime.

After the reviewed inactive deployment, provision only a synthetic account, set the bounded staging environment variables without publishing credentials, and redeploy through the coordinated staging release. Confirm other signed-in owners still receive 503 for every export route, then test the synthetic request, ready archive, authenticated download, expiry, and two cleanup passes. The second pass is due 24 hours after the first. Do not delete the synthetic account until its durable cleanup task has completed; the scoped cleanup query needs the request row to identify the archive. Stopping build while retaining cleanup requires moving the build cutoff into the past. The review checkpoint does not stop cleanup: an archive published at the end of the build window may need its first cleanup pass 24 hours later and its second pass another 24 hours after that. Cron delay or provider retries can make both later. Check that the synthetic owner's ready requests and durable cleanup tasks are gone before removing the proof settings. Removing the acknowledgment stops both immediately but may strand a task, so use that emergency stop only with an incident and recovery plan. The staging proof skips generic incident pruning to avoid changing another account's evidence. An incident requires a separate, reviewed resolution and retention check.

No staging export has run yet. The request and cleanup windows, credentials, permissions, archive bytes, and provider behavior remain unverified until the staged test actually passes. Neither this staging authorization nor its evidence permits production activation.

If a release is running when the owner removes approval, wait for it to finish, dispatch a fresh coordinated rollback release, and verify both deployments reflect the new mode. Do not consider a variable edit alone a rollback. This retains unscoped durable cleanup for archives already accepted. Do not remove cleanup-only approval until database and R2 evidence confirms existing tasks and multipart uploads are resolved.
