# Messaging action ownership completion for PR #150

Status: implementation handoff. This work completes the open backend refactor PR #150 before its squash merge. Do not open a separate PR or merge it automatically.

## Agreed architecture

Messaging is a domain with four subfeatures: `conversations`, `messages`, `push`, and `realtime`. Each subfeature contains action directories. The `messaging.routes.ts` entry point registers middleware and action routes only. An action owns its route, endpoint-specific persistence, schemas, and tests. Add a service only when it owns meaningful business rules or coordination; simple authorized reads may use route to repository. Do not add pass-through services or copy shared security invariants to achieve folder symmetry.

Keep shared runtime code only for operations genuinely needed by multiple actions. Put same-subfeature reusable operations in `<subfeature>/shared/` and cross-subfeature operations in `messaging/shared/`. Name each file after a reusable capability, such as `require-conversation-member.ts`, `message-projection.ts`, `append-conversation-change.ts`, or `conversation-lock.ts`, rather than a feature-wide repository containing unrelated action methods. Shared transactional helpers accept the caller's transaction and never open an independent transaction during a write. Provider adapters remain under `src/infrastructure/`.

Tests remain colocated under `<action>/__tests__/`, using action-prefixed filenames: `<action>.route.test.ts`, `<action>.service.test.ts`, and `<action>.repository.integration.test.ts` when those layers exist. Shared operation tests go under the appropriate `shared/__tests__/`. Action-specific fixtures live inside that action's `__tests__/`. Reusable test-only support belongs in `apps/api/test/support/messaging/`. Boundary-rule positive/negative fixtures belong under `apps/api/test/boundaries/`, not production action folders; the boundary checker must resolve their intended virtual source location correctly without weakening enforcement. Test discovery and lint rules must cover nested and action-prefixed files.

## Authorization contract

Hono middleware verifies identity and broad feature gates, currently session and username setup. Future coarse role or subscription entitlement middleware may be added only when product rules exist and server-owned records are authoritative; this refactor does not add roles, plans, or billing. Each action still authorizes its specific resource. Simple reads use actor-scoped queries; mutations check membership, ownership, block/request state, and any racing predicate inside their write transaction with existing lock order. Never treat admin as an implicit bypass for private messages. Preserve 401 versus private 404 versus 403 behavior and no-store headers.
