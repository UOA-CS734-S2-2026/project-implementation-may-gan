# Backend action boundaries refactor

Status: implementation handoff. Base: updated `main` at `d326083`. Target: one backend-only PR, squash merged. This document describes desired structure, not existing behavior.

## Outcome and invariants

Organize `apps/api/src/features` by owning feature and then by HTTP action. A feature root contains action directories, optional grouping directories (`messages`, `conversations`, `push`, `realtime`), and an optional `shared/` directory. The sole permitted feature-root source file is a thin `<feature>.routes.ts` registration entry point. Do not put HTTP handlers, contracts, stores, or business logic at the feature root. A route file within an action is the HTTP adapter, not a competing architecture: it defines the endpoint, validates input, authenticates, calls the operation, and maps the result to HTTP. Each HTTP action must have its own route and route test. Put meaningful service, repository, contract, and their tests in the action folder when they are action-owned; do not manufacture pass-through layers or duplicate shared stores to meet a file-count quota.

No changes to endpoint paths or methods, OpenAPI operation IDs or schemas, authentication and authorization, trusted-origin handling, header/cache behavior, error codes, transaction boundaries or locking, runtime/Cloudflare delivery, migrations, or client-facing behavior. Maintain existing tests and add targeted route coverage for newly split endpoints. Keep this PR backend-only, except for necessary documentation and lint tooling. Do not regenerate clients unless the baseline comparison proves an existing generated artifact is stale, in which case report and separate the change rather than hiding contract drift in this PR.

## Target map and task sequence

1. Establish lint boundary rules and their positive/negative fixtures first. Match action-prefixed names such as `send-message.service.ts`, not only literal `service.ts`. Cover relative, aliased, re-export, dynamic, and type-only imports as supported by the chosen tool; document any limitation. Imports inside an action may target that action, same-feature `shared/`, approved `src/http` and `src/infrastructure` adapters, and approved workspace packages. Action internals may not import a sibling action or another feature's internals. A feature registrar may import its own action route registration exports; `app.ts` may compose registration functions and concrete dependencies. Tests may import the action under test and app/test harness, not unrelated action internals. Shared modules may not import action internals. Keep provider-specific Better Auth and non-HTTP authorization modules as documented exceptions, not fake CRUD actions. Add a guard that catches feature-root implementation files except `<feature>.routes.ts`, or document and test precise exceptions. Make the guard part of the root lint command/CI.
2. Messaging messages: preserve `send-message/`; split `messages/message-actions.route.ts` into `edit-message/`, `unsend-message/`, `set-reaction/`, and `remove-reaction/` action-local routes/tests. Relocate `messages/message.contract.ts` to narrowly named same-feature `shared/` contracts or action contracts as appropriate. Move grouped service tests to action ownership where practical. Shared message write transaction interfaces and common projections remain `messaging/shared/`, with their integration tests adjacent to the shared implementation when applicable.
3. Messaging conversations: split `conversations/conversation.route.ts` into `create-direct-conversation/`, `list-conversations/`, `get-conversation/`, `get-messaging-unread/`, `list-messages/`, `get-message/`, `resolve-message-request/`, `mark-conversation-read/`, and `list-conversation-changes/` (names may be adjusted to match operation intent, not paths). Move grouped conversation contracts, reader/store, and grouped route/integration tests to the owning action or `messaging/shared/` when truly shared. Preserve transaction ownership and authorization in database operations. No route may depend on a sibling action's service or repository.
4. Messaging push and realtime: split `push/push-device.route.ts` into register/unregister device actions; split ticket and connect into `realtime/issue-ticket/` and `realtime/connect/` with corresponding route tests. Keep WebSocket connect a protocol adapter outside JSON OpenAPI. Move shared device/ticket persistence only if ownership is clear; provider FCM and Durable Object adapters stay in `src/infrastructure/`.
5. Consolidate messaging registration: `app.ts` calls `registerMessagingRoutes(...)` once. That feature registrar calls every messaging action registrar, including push and realtime, without containing handler logic. Keep dependency injection testable and preserve registration order and unavailable behavior. Do not add a second authentication handler or duplicate middleware accidentally.
6. Other features: move feature-root relationship contracts, repository, service, and integration test to `relationships/shared/` if truly common; retain thin `relationships.routes.ts`. Move `media/reservation-status.ts` into `media/shared/`; retain thin `media.routes.ts`. Normalize non-action folder and generic action filenames under media and system, including `media/complete/` and `system/test-contracts/`, without changing their public behavior. Audit `posts/` and `posting-days/` for rule compliance, moving only what violates it. Keep `auth/` as a Better Auth provider integration and `permissions/` as a non-HTTP authorization module with explicit, narrow lint exemptions. Keep system Hyperdrive compatibility/test worker entrypoints in their supported runtime location rather than inventing public actions.
7. Update architecture documentation to distinguish feature registrars, action routes, action-local logic, feature-shared logic, and infrastructure. Replace outdated statements claiming messaging is only planned where necessary; avoid unrelated documentation rewrites.

Use small internal commits per stage for review, but open one refactor-only PR and request squash merge. Do not split this into multiple externally merged PRs.

## Import enforcement acceptance

Use ESLint with a path-aware boundary rule or a dependency-graph check integrated into `pnpm lint`; choose the simplest mechanism that resolves this repository's TypeScript imports reliably. Add fixtures/tests that demonstrate sibling-action imports fail, feature-to-feature internal imports fail, action-to-own-feature-shared imports pass, feature registrar-to-action-route imports pass, `app.ts` composition passes, and type-only imports are subject to the same boundary. Update existing ESLint file globs for action-prefixed `*.route.ts`, `*.service.ts`, and `*.contract.ts`; do not quietly drop current Hono/DB/route restrictions. Keep tests from bypassing production-source boundaries.

Stop and request review rather than changing behavior to satisfy the structure if a move requires changing a public contract, security boundary, database transaction or lock, worker runtime semantics, or generated client output. Deliver a PR summary including the before/after path map, exact exceptions, baseline contract comparison, test results/skips, and explicit squash-merge request.
