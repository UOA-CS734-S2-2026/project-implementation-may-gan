# Drizzle query-builder refactor

Status: implemented, pending squash-merge review. Started from `main` at `3a547ce` and merged the newer `main` at `9f0998f`. PR branch: `refactor/drizzle-query-builders`. This is a database access refactor, not a product or schema redesign. Do not merge automatically.

## Result

The initial base had 102 production `.execute(` calls across 39 files in `apps/api/src`. The updated `main` added two more calls in new direct-conversation and profile reads. All 104 calls now use Drizzle builders. The shared runtime relationship-pair lock in `packages/db/src/relationship-pair-lock.ts` also uses a builder. The 11 `.execute(` calls left in `packages/db/src/index.ts` belong to database connection, migration, and diagnostic probes, not API repositories. Test fixtures can still use raw SQL.

`pnpm lint` runs an AST check that rejects API runtime `execute` calls and typed execute capabilities while allowing tests and database diagnostics. Final verification on the merged branch passed `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm --filter @dayli/api test:realtime`, `pnpm generate:clients:check`, and the disposable PostgreSQL verifier (40 API integration files, 145 tests). OpenAPI, generated clients, and schema definitions have no diff against the updated `main`.

## Goal and scope

Replace `database.execute(sql`...`)` and `tx.execute(sql`...`)` in API runtime data access with Drizzle's typed `select`, `insert`, `update`, and `delete` builders. SQL expressions **inside** those builders are allowed for PostgreSQL-specific behavior such as advisory locks, composite cursors, aggregates, `greatest`, `exists`, `returning`, row locking, and conflict handling. The target is not to ban SQL fragments. Where a feature genuinely cannot be expressed safely with a builder, stop, document the exact operation and evidence, and request review before adding a narrowly justified exception. Do not disguise whole raw statements as a `sql` expression in a builder merely to satisfy a lint rule.

Scope includes `apps/api/src` feature repositories, feature-shared persistence, app composition queries, auth lifecycle queries, and infrastructure data access (jobs, push, realtime). Tests may use raw SQL for fixture setup, assertions, and database probes. `packages/db` migration machinery, schema definitions, database setup, diagnostic probes, and database-specific tests are explicit exceptions. Do not redesign `packages/db` schema or migrate tables as a side effect. Keep Drizzle over postgres.js and Hyperdrive, with the existing per-invocation client close lifecycle.

This refactor must not alter public API paths, operation IDs, generated OpenAPI/clients, row visibility, permission/privacy decisions, idempotency, SQL predicates or ordering, transaction scope, locks and lock order, timestamps, counters, outbox writes, realtime or push delivery, error mapping, or database migrations. Especially preserve `NOT_FOUND` privacy for nonmembers and postcommit dispatch.

## Inventory and risk classification

Before editing, produce a checked-in matrix of every runtime `.execute(` in `apps/api/src` (excluding tests), with file, operation, table, Drizzle target, currently observed behavior, owner test, and risk category. Current base includes calls in messaging conversation and message actions/shared operations, push registration and ticket issuance, relationship shared repositories, media reservation, post creation and username profile, auth route, app session resolver, jobs outbox, push destinations, realtime publisher and Durable Object. Newly merged `posts/get-post` and `posts/list-feed` use typed builders already; preserve them as regression examples. Audit for other raw statements not spelled `.execute(` and dynamic or delegated calls. Include a baseline count from `rg` and do not mark complete until every in-scope call is converted or explicitly reviewed as an exception.

Classify:

1. Simple actor-scoped reads and deletes, including `get-message`, `unregister-device`, username lookup, and session lookup. Lowest risk.
2. Joins, aggregation, pagination and projections, including inbox, feed-like reads, unread counts, reactions, reply previews, and outbox claims. Preserve membership filters, SQL null behavior, stable tie-break ordering and cursor precision.
3. Writes, upserts and `returning` projections, including push token rotation, reaction writes, changes and outbox records. Preserve conflict targets, row counts, and order of writes.
4. Lock-sensitive multiwrite transactions, including conversation creation, send/edit/unsend/reaction, read/request resolution, relationship pair locking, daily post uniqueness, and reservation locks. Highest risk. Keep all predicate reads and writes in the same transaction with identical advisory and row locks.
5. Infrastructure jobs and session/realtime checks. Preserve leases, fencing, retry behavior, exact session expiry and security filters.

The messaging schema currently declares several PostgreSQL `bigint` sequence and cursor columns using Drizzle `{ mode: "number" }`, whereas existing raw-row mapping often converts PostgreSQL values with `BigInt` or `String`. **Do not silently lose precision** through typed column decoding. Select `sql<string>` cast expressions or use an equivalent verified mapping for values that may exceed `Number.MAX_SAFE_INTEGER`; avoid changing schema column modes without a separately reviewed impact analysis. Cursor activity timestamps currently preserve microseconds via `to_char`; a JavaScript `Date` round trip can truncate them. Preserve the exact cursor string format, ordering and comparison with focused real-Postgres tests.

## Execution tickets

Each ticket is a focused internal commit and reviewed diff. Do not hand the entire inventory to one implementor in a single pass.

0. Baseline and tooling: capture generated OpenAPI and client artifacts, route inventory, unit/worker/Postgres discovery, `rg` inventory and migration journal. Confirm available Drizzle v0.45 APIs for `for('update')` (including joined rows), conflict updates, SQL-only expressions for advisory locks, correlated subqueries, `returning`, and transactions using small disposable Postgres characterization tests. If a lock API cannot reproduce existing lock semantics, stop and record the exception rather than weakening it.
1. Simple reads: one action per ticket, starting with messaging `get-message`, `list-messages` and `get-conversation`, then username, auth/session and push unregister. Rewrite the query inside its existing action repository, retain actor scoping, add precise integration assertions, and keep API output identical. Move no folders and add no pass-through service.
2. Remaining read projections and pagination: one repository per ticket across messaging conversations and relationship reads, then jobs/realtime reads. Characterize microsecond cursor and `bigint` boundaries, reaction and reply projection, unread aggregates, membership and blocks. Do not introduce a second query or N+1 behavior without review.
3. Simple writes: reaction CRUD, token registration and uncomplicated relationship writes, followed by action-specific update helpers. Keep exact `on conflict`, `returning`, deleted row counts, and token/session revalidation semantics.
4. Transactional messaging and relationship writes: one action per ticket, using Drizzle builders on the **caller-owned transaction**. Preserve pair advisory lock identity, lock acquisition order, `FOR UPDATE`, idempotency, change/outbox atomicity and no-op handling. Verify two-client concurrency and rollback against real Postgres after each ticket.
5. Infrastructure writes: outbox claims/leases/fencing, job dispatch, push destinations, and realtime publication. Treat as high risk and use integration tests for retries and ownership. Keep provider-specific network calls outside SQL transactions.
6. Finish coverage and enforcement: rerun the inventory and establish a lint/AST check that rejects new `.execute(` in in-scope production API data access, with positive tests for allowed migrations/diagnostics/test fixtures and negative tests for feature, infrastructure and type-only bypasses. Do not count string matching alone as sufficient if false positives or bypasses are found. Document any reviewed exceptions with a named path and reason. Update `docs/backend-architecture.md` with the rule that repositories use builders by default and may use bounded SQL expressions within them.
